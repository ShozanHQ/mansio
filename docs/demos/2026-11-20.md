What moved in mansio from 2026-11-13 to 2026-11-20, by theme, with steps you can run.
You need a checkout of this repository, the Rust toolchain pinned in `rust-toolchain.toml`, `curl` and `jq`. No Docker.

## The steps

### 1. Start the server

Run this in one terminal. CI starts the same server itself.

```sh
cd mansio
export MANSIO_DEMO_DIR=$(mktemp -d)
MANSIO_BROKER=memory MANSIO_TOKEN=demo-token MANSIO_SINK_PATH="$MANSIO_DEMO_DIR/sink.jsonl" \
  MANSIO_SNAPSHOT_DIR= cargo run -p mansio-server
```

In a second terminal, for every step after this one:

```sh
cd mansio
cargo build -p mansio -p mansio-server
export PATH="$PWD/target/debug:$PATH" MANSIO_URL=http://127.0.0.1:7070 MANSIO_TOKEN=demo-token
```

### 2. See a queue's live work

Publish three items, claim one, then list the queue and look at single items.

```bash
A=11111111-1111-4111-8111-111111111111
B=22222222-2222-4222-8222-222222222222
C=33333333-3333-4333-8333-333333333333
for id in $A $B $C; do
  mansio work publish --tenant demo --queue builds --type build.requested --source ci --id "$id" --data '{}' >/dev/null
done
lease=$(mansio work pull --tenant demo --queue builds --consumer w1 | jq -r .lease_id)
mansio work list --tenant demo --queue builds | jq -c '.items[] | {item_id, state, consumer}'
mansio work show --tenant demo --queue builds --item "$B" | jq -e '.state == "claimable" and .envelope.id == "'"$B"'"'
```

You should see the claimed item first as `leased` to `w1`, the other two `claimable`, in publish order, then `true`:

```text
{"item_id":"11111111-1111-4111-8111-111111111111","state":"leased","consumer":"w1"}
{"item_id":"22222222-2222-4222-8222-222222222222","state":"claimable","consumer":null}
{"item_id":"33333333-3333-4333-8333-333333333333","state":"claimable","consumer":null}
true
```

Once the claimed item is acknowledged it leaves the list and shows only as finished:

```bash
mansio work ack --tenant demo --queue builds --item "$A" --consumer w1 --lease-id "$lease" >/dev/null
mansio work list --tenant demo --queue builds | jq -e '.items | length == 2'
mansio work show --tenant demo --queue builds --item "$A" | jq -c .
curl -fsS -H "Authorization: Bearer $MANSIO_TOKEN" "$MANSIO_URL/v1/settings" \
  | jq -c '{work_list_default_count, work_list_max_count}'
```

```text
true
{"item_id":"11111111-1111-4111-8111-111111111111","state":"finished"}
{"work_list_default_count":100,"work_list_max_count":1000}
```

### 3. Work is resent by its id, never by a key

A repeat of an id answers 409, which means the first send was stored. A key on a work publish is refused with 400, where it used to be ignored.

```bash
if out=$(mansio work publish --tenant demo --queue builds --type build.requested --source ci --id "$B" --data '{}' 2>&1); then false; fi
echo "$out" | grep -F '409'
curl -sS -o "$MANSIO_DEMO_DIR/keyed.json" -w '%{http_code}\n' -X POST \
  -H "Authorization: Bearer $MANSIO_TOKEN" -H 'content-type: application/json' \
  "$MANSIO_URL/v1/tenants/demo/work/builds/items" \
  -d '{"type":"build.requested","source":"ci","idempotencykey":"k1","data":{}}'
jq -r .error.message "$MANSIO_DEMO_DIR/keyed.json"
mansio work list --tenant demo --queue builds | jq -e '.items | length == 2'
```

```text
mansio: refused (409 Conflict): conflict: builds already has an item with id 22222222-...: an id is not used again, even when the item is done
400
idempotencykey is not taken by work_publish: a work item is made safe to send again by its id, and a repeated id answers 409
true
```

### 4. A server that expects a peer refuses to run without ownership

This is what the two-server Compose profile's second server now does when `MANSIO_OWNER_TTL_SECONDS` is not set. It stops at its settings, before it binds a port.

```bash
server="$(dirname "$(command -v mansio)")/mansio-server"
if out=$(MANSIO_EXPECT_PEERS=true MANSIO_BROKER=memory MANSIO_TOKEN=demo-token MANSIO_SNAPSHOT_DIR= "$server" 2>&1); then false; fi
echo "$out" | grep -F 'MANSIO_EXPECT_PEERS is not valid'
```

```text
    MANSIO_EXPECT_PEERS is not valid: true needs MANSIO_OWNER_TTL_SECONDS set, to the same value (3 or more) on every server, or two servers could lease the same item
```

The two-server stack itself needs Docker and Iggy, so CI shows it: the [`e2e` job on `main`](https://github.com/ShozanHQ/mansio/actions/workflows/ci.yml?query=branch%3Amain) starts both servers with an owner ttl.

## Architecture

```mermaid diff [Reading the work queue, and the second server's start gate]
 flowchart LR
     C[client: HTTP, CLI, MCP] --> W[work routes: publish, pull, extend, ack, fail]
     W --> Q[tenant queue state]
+    C --> R[work_list, work_show]
+    R -->|read only| Q
     S2[second server] --> SET[settings]
-    SET --> RUN[serve, ownership optional]
+    SET -->|MANSIO_EXPECT_PEERS and ttl 0: refuse| STOP[exit with the reason]
+    SET --> RUN[serve with ownership]
     %% ref node:R [[21c00d8:crates/mansio-server/src/work_api.rs#L143-L221]]
     %% ref node:SET [[21c00d8:crates/mansio-server/src/settings.rs#L668-L679]]
```

- Data path: two read-only routes on the queue state that claims are decided from, so what an operator sees is what a worker would get. No new record, snapshot format or replay change.
- Settings: `MANSIO_WORK_LIST_DEFAULT_COUNT` and `MANSIO_WORK_LIST_MAX_COUNT` size a page; `MANSIO_EXPECT_PEERS` makes a missing ownership ttl a start error.
- Dependency: `toml_edit`, already in the tree, becomes a test-only dependency of the `mansio` crate, to check the release configuration.
- No new crate, service or protocol.

## What moved

### An operator can see the work in a queue

Until now a queue was a black box: work went in and came out, and nothing showed what was waiting, who held what, or why an item was not moving. A page of a queue's live items now lists each one in publish order with its state (claimable, leased, backoff), attempt, holder and lease expiry or retry time, filtered by state and paged. One item can be read by id with its message; a finished item shows only that it is finished. The same reads are a CLI command, an MCP tool and an HTTP route, under the same permission as reading the queue: [[21c00d8:crates/mansio-server/src/work_api.rs#L143-L221]]. (#103)

### The promise says what mansio does

The README and the architecture note said work is never done twice. That overstated it: an item whose lease ends goes to another consumer, so a worker must make its effect idempotent. The guarantee now reads: no item lost, each acknowledged at most once, delivered at least once, [[21c00d8:README.md#L216-L223]]. In the same spirit, a work publish with an idempotency key, which was accepted and did nothing, now answers 400 and points at the item's id, [[21c00d8:crates/mansio-server/src/app.rs#L679-L681]]. The CLI and MCP drop the flag for work. Install now says to build from a clone until the first release. (#102, #101)

### Safer to run by default

The two-server Compose profile could start a second server without tenant ownership, and two servers would then lease the same item. Its second server now runs with `MANSIO_EXPECT_PEERS=true` and refuses to start unless an owner ttl is set, naming both settings: [[efd7bbc:compose.yaml#L200-L220]]. Separately, the server logs a warning at start for each development credential from `compose.yaml` still in use, naming the setting and never the value: [[21c00d8:crates/mansio-server/src/settings.rs#L527-L540]]. (#100, #95)

### The first release, one blocker closer

The release run stopped on a release-plz setting that the tool rejects; that setting is gone and a test checks the file against the keys release-plz takes, [[crates/mansio/tests/release_config.rs]]. The dependency audit, red since two crates mansio pulls in through Iggy were marked unmaintained, passes again with both acknowledged by id until 2026-12-18, [[deny.toml]]. What remains is a repository setting: GitHub refuses to let the workflow open the release pull request. (#97, #94)

## State models

`cargo test -q --locked -p mansio-models` on this commit: 18 tests pass. Every rule of the work-item model holds. The seeded-bug model breaks the one rule it is built to break, which is not a finding.

| Rule | work-item | work-item-ack-on-expired-lease (seeded bug) |
|---|---|---|
| always: an item has at most one live lease | holds | holds |
| always: an ack or extend with a lease that is not live is refused | holds | broken, as seeded |
| always: an item is acked at most once | holds | holds |
| always: an item past the attempt cap is in dead and nowhere else | holds | holds |
| eventually: every item ends acked or dead | holds | holds |
| sometimes: an item is acked after a retry | holds | holds |
| sometimes: an item reaches dead | holds | holds |

No model or rule was added or changed this week, and no chart changed: [[crates/mansio-models/charts/work-item.md]], [[crates/mansio-models/charts/work-item-ack-on-expired-lease.md]].
