# Friday demo, 2026-11-27: the week in mansio

What moved in mansio from 2026-11-20 to 2026-11-27, by theme, with steps you can run.
You need a checkout of this repository, the Rust toolchain pinned in `rust-toolchain.toml`, `curl` and `jq`. No Docker.

## This week

- A worker is now one line. `mansio work run -- CMD` claims one item, runs your command with the item on its standard input, keeps the lease alive while the command runs, and acks or fails the item by how the command ends.
- A machine can react to events with one line. `mansio watch -- CMD` runs your command for each envelope of a topic and moves its place only when the command succeeds, so nothing is skipped on a failure or a restart.
- Neither command hands its credential to the program it runs: the token is removed from the command's environment, so only mansio extends, acks or fails.
- Together they mean a machine can pick up and do work with nothing but the `mansio` binary and a shell script: no client library, no code written against the API.
- The dependency check passes on every pull request again, after a fix in the `url` library was taken into both lockfiles.

Numbers: 4 pull requests merged, 0 releases cut, 0 issues closed.

Biggest risk: mansio has still never been released, so the two new commands reach nobody who does not build from a clone. Every [release run](https://github.com/ShozanHQ/mansio/actions/workflows/release.yml) on `main` this week failed at the same place as last week: GitHub answers 403 when the workflow opens the release pull request, because the repository does not allow GitHub Actions to create pull requests ([newest run](https://github.com/ShozanHQ/mansio/actions/runs/45677260686)).

## The steps

### 1. Start the server

Run this in one terminal. CI starts the same server itself.

```sh
cd mansio
export MANSIO_DEMO_DIR=$(mktemp -d)
MANSIO_BROKER=memory MANSIO_TOKEN=demo-token MANSIO_SINK_PATH="$MANSIO_DEMO_DIR/sink.jsonl" \
  MANSIO_SNAPSHOT_DIR= cargo run -p mansio-server
```

In a second terminal, for every step after this one:

```sh
cd mansio
cargo build -p mansio -p mansio-server
export PATH="$PWD/target/debug:$PATH" MANSIO_URL=http://127.0.0.1:7070 MANSIO_TOKEN=demo-token
```

### 2. A worker in one line

Publish one item, then let `work run` claim it and run a script for it. The script reads the item from its standard input and writes down what it was given.

```bash
A=11111111-1111-4111-8111-111111111111
mansio work publish --tenant demo --queue builds --type build.requested --source ci --id "$A" --data '{"repo":"acme/site"}' >/dev/null
cat >"$MANSIO_DEMO_DIR/build.sh" <<'EOF'
#!/bin/sh
jq -c '{id, data}' >"$MANSIO_DEMO_DIR/got.json"
echo "item=$MANSIO_ITEM_ID queue=$MANSIO_QUEUE attempt=$MANSIO_ATTEMPT token=${MANSIO_TOKEN:-none}" >"$MANSIO_DEMO_DIR/env.txt"
EOF
chmod +x "$MANSIO_DEMO_DIR/build.sh"
mansio work run --tenant demo --queue builds --consumer worker-1 -- "$MANSIO_DEMO_DIR/build.sh" | jq -r .type
cat "$MANSIO_DEMO_DIR/got.json" "$MANSIO_DEMO_DIR/env.txt"
mansio work show --tenant demo --queue builds --item "$A" | jq -c .
```

You should see the type of the ack `work run` sent, the item as the script read it, the script's environment with no token in it, and the item finished:

```text
mansio.work.acked
{"id":"11111111-1111-4111-8111-111111111111","data":{"repo":"acme/site"}}
item=11111111-1111-4111-8111-111111111111 queue=builds attempt=1 token=none
{"item_id":"11111111-1111-4111-8111-111111111111","state":"finished"}
```

With nothing in the queue it runs nothing, prints nothing and exits 0, so a shell loop or a service manager can call it again and again:

```bash
mansio work run --tenant demo --queue builds --consumer worker-1 -- "$MANSIO_DEMO_DIR/build.sh" | wc -c | tr -d ' '
```

```text
0
```

### 3. A command that fails gives the item back

The command's exit status decides. A non-zero exit fails the item with a reason that says so, `work run` exits 3, and the item waits for its retry.

```bash
B=22222222-2222-4222-8222-222222222222
mansio work publish --tenant demo --queue builds --type build.requested --source ci --id "$B" --data '{}' >/dev/null
code=0
mansio work run --tenant demo --queue builds --consumer worker-1 -- sh -c 'cat >/dev/null; exit 7' >"$MANSIO_DEMO_DIR/fail.json" || code=$?
echo "exit $code"
jq -c '{type, reason: .data.reason}' "$MANSIO_DEMO_DIR/fail.json"
mansio work show --tenant demo --queue builds --item "$B" | jq -c '{state, attempt}'
```

```text
exit 3
{"type":"mansio.work.failed","reason":"the command exited with status 7"}
{"state":"backoff","attempt":1}
```

### 4. React to each event, and move on only when the command succeeds

Publish two facts, then watch the topic as a named consumer with a command. Each envelope is printed and its offset committed only after the command exits 0 for it.

```bash
for n in 1 2; do
  mansio publish --tenant demo --topic facts.build --type build.finished --source ci --data "{\"n\":$n}" >/dev/null
done
mansio watch --tenant demo --topic facts.build --consumer starter --limit 2 -- \
  sh -c 'jq -c "{offset: env.MANSIO_OFFSET, type: env.MANSIO_EVENT_TYPE, n: .data.n}" >>"$MANSIO_DEMO_DIR/seen.jsonl"' \
  | jq -c .data
cat "$MANSIO_DEMO_DIR/seen.jsonl"
```

You should see the two envelopes the watcher printed, then what the command saw for each:

```text
{"n":1}
{"n":2}
{"offset":"0","type":"build.finished","n":1}
{"offset":"1","type":"build.finished","n":2}
```

Now a third fact and a command that always fails. With `MANSIO_WATCH_ATTEMPTS=2` the watcher runs it twice, exits 3 and commits nothing, so the next start, here with a command that succeeds, resumes at the same envelope:

```bash
mansio publish --tenant demo --topic facts.build --type build.finished --source ci --data '{"n":3}' >/dev/null
code=0
MANSIO_WATCH_ATTEMPTS=2 MANSIO_WATCH_RETRY_BASE_MILLIS=100 \
  mansio watch --tenant demo --topic facts.build --consumer starter -- \
  sh -c 'cat >/dev/null; echo run >>"$MANSIO_DEMO_DIR/tries.txt"; exit 1' 2>/dev/null || code=$?
echo "exit $code, runs $(wc -l <"$MANSIO_DEMO_DIR/tries.txt" | tr -d ' ')"
mansio watch --tenant demo --topic facts.build --consumer starter --limit 1 -- sh -c 'cat >/dev/null' | jq -c .data
```

```text
exit 3, runs 2
{"n":3}
```

## Architecture

```mermaid diff [A command run for each event, and for each work item]
 flowchart LR
     T[topic] -->|poll| WA[mansio watch]
-    WA -->|print, then commit| P[consumer position]
+    WA -->|envelope on stdin| C1[your command]
+    C1 -->|exit 0: print, then commit| P[consumer position]
+    C1 -->|non-zero: wait, run again| WA
     Q[work queue] -->|work pull| L[lease]
-    L --> H[your code: extend, ack, fail over the API]
+    L --> R[mansio work run]
+    R -->|item on stdin, no token| C2[your command]
+    R -->|extend while it runs| Q
+    C2 -->|exit 0: ack, else fail| R
     %% ref node:R [[d4bd884:crates/mansio/src/run.rs#work_run]]
     %% ref node:WA [[2b4e644:crates/mansio/src/watch.rs#run_command]]
     %% ref node:C2 [[3670eb6:crates/mansio/src/child.rs#start]]
```

- Data path: the CLI now starts a program of the caller's and decides the commit, the ack or the fail from its exit status. The server, its routes and its records did not change: both commands use the operations that were already there.
- Settings: `MANSIO_WATCH_RETRY_BASE_MILLIS`, `MANSIO_WATCH_RETRY_CAP_MILLIS` and `MANSIO_WATCH_ATTEMPTS` shape the watcher's retries; `MANSIO_RUN_EXTEND_AT_PERCENT` and `MANSIO_RUN_STOP_GRACE_SECONDS` shape when the runner extends a lease and how long it lets a command end.
- Dependency: the `mansio` crate turns on tokio's `process` feature, to start and reap the command. `url` moves to 2.5.9 in both lockfiles.
- No new crate, service or protocol.

## What moved

### A worker with nothing but mansio and a script

Until now, doing work from a queue meant writing code against four operations: pull, extend on a timer, then ack or fail. `mansio work run` is that loop for one item: it claims, runs the command with the item on its standard input, extends the lease as it runs down, and acks on exit 0 or fails with the reason otherwise, [[d4bd884:crates/mansio/src/run.rs#work_run]]. A lost lease kills the command and sends nothing, so a second worker that now holds the item is not contradicted; a signal lets the command finish for a grace period before it is stopped. It is at least once, as mansio is: the command's effect should be safe to repeat for one item id, [[d4bd884:README.md#L401-L451]]. (#109)

### React to events, and never skip one

`mansio watch` could print a topic's envelopes; acting on them was left to a pipe, which loses its place when the consumer of the pipe fails. With a command after `--`, the watcher runs it for each envelope in order and commits the offset only after the command exits 0, [[2b4e644:crates/mansio/src/watch.rs#run_command]]. A failing command is run again for the same envelope after a wait that doubles to a cap, and an attempt limit turns a stuck envelope into exit 3 with nothing committed. This is what lets one machine start a worker when work is published, with generic commands only, [[d4bd884:README.md#L378-L400]]. (#107)

### The command never holds the credential

Both commands start the caller's program through one place that removes `MANSIO_TOKEN` from its environment, [[3670eb6:crates/mansio/src/child.rs#start]]. The program gets the item or the envelope and a few names in its environment, and cannot extend, ack, fail or publish by itself. Neither command is an MCP tool, since a tool call cannot run a program and wait for it; the test that holds the CLI and MCP to one list names both exceptions, [[d4bd884:crates/mansio/src/ops.rs#is_tool]]. (#107, #109)

### Pull requests are checked again

The dependency check went red on every pull request when an advisory landed against the `url` library. Both lockfiles now hold 2.5.9, and the check is green on `main`, [[ef68220:Cargo.lock]]. (#108)
