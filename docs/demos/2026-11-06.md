# Friday demo, 2026-11-06: what mansio shipped this week

Every pull request merged to `main` since 2026-10-30, what each changes for
someone running mansio, and a walkthrough you can follow on your own machine.
You need a checkout of this repository, a Rust toolchain (the one pinned in
`rust-toolchain.toml`), `curl` and `jq`, on macOS or Linux. No Docker. The
steps use the memory broker, which keeps everything in the server's memory and
forgets it when the server stops.

CI runs every `bash` block below, in order, against a fresh memory-broker
server, with
[`.github/scripts/demo-check.sh`](../../.github/scripts/demo-check.sh). A step
that no longer works as written fails the build.

To read this file with its links to the code, open it in the diffmap viewer;
[`docs/demos/README.md`](README.md) says how. Each row below links the code
it describes.

## The steps

### 1. Start the server

This block is `sh`, not `bash`, so the checker does not run it: it starts the
server itself, with the same settings, and leaves `MANSIO_URL`,
`MANSIO_TOKEN` and `MANSIO_DEMO_DIR` set for the steps after it. Run this in
one terminal and the rest in another.

```sh
cd mansio
export MANSIO_DEMO_DIR=$(mktemp -d)
MANSIO_BROKER=memory MANSIO_TOKEN=demo-token MANSIO_SINK_PATH="$MANSIO_DEMO_DIR/sink.jsonl" \
  MANSIO_SNAPSHOT_DIR= cargo run -p mansio-server
```

In the other terminal:

```sh
cd mansio
cargo build -p mansio
export PATH="$PWD/target/debug:$PATH" MANSIO_URL=http://127.0.0.1:7070 MANSIO_TOKEN=demo-token
export MANSIO_DEMO_DIR=<the directory the first terminal made>
```

### 2. The server is up

```bash
curl -fsS "$MANSIO_URL/healthz"
```

```text
{"status":"ok"}
```

### 3. `data` comes back as published (#44)

```bash
mansio publish --tenant demo --topic facts.build --type build.finished \
  --source ci --data '{"big":12345678901234567890,"price":1.10,"e":1e2}'
mansio poll --tenant demo --topic facts.build | tee "$MANSIO_DEMO_DIR/poll.txt"
grep -F '12345678901234567890' "$MANSIO_DEMO_DIR/poll.txt"
grep -F '1.10' "$MANSIO_DEMO_DIR/poll.txt"
grep -F '1e2' "$MANSIO_DEMO_DIR/poll.txt"
```

The first command prints the envelope as stored, the second the envelopes of
the topic, one a line. Each has `"data":{"big":12345678901234567890,"price":1.10,"e":1e2}`:
the digits are the ones you sent, not `1.2345678901234567e19`, `1.1` or `100`.

### 4. A publish with the same idempotency key is not stored twice (#20)

```bash
first=$(mansio publish --tenant demo --topic facts.build --type build.finished \
  --source ci --data '{"n":1}' --idempotency-key demo-key-1)
second=$(mansio publish --tenant demo --topic facts.build --type build.finished \
  --source ci --data '{"n":2}' --idempotency-key demo-key-1)
test "$(jq -r .id <<<"$first")" = "$(jq -r .id <<<"$second")"
```

The block prints nothing and succeeds when both publishes returned the same
envelope, the first one: `{"n":1}`, the same `id`. The second publish
answered 200 and stored nothing; the first answered 201. With `curl` you see
the status:

```bash
code=$(curl -sS -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $MANSIO_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"source":"ci","type":"build.finished","idempotencykey":"demo-key-1","data":{"n":3}}' \
  "$MANSIO_URL/v1/tenants/demo/topics/facts.build/messages")
echo "$code"
test "$code" = 200
```

```text
200
```

### 5. The sink holds whole lines (#45)

Step 1 gave the server a sink file. Every durable publish is in it, one
complete JSON line each.

```bash
test -s "$MANSIO_DEMO_DIR/sink.jsonl"
jq -e . "$MANSIO_DEMO_DIR/sink.jsonl" >/dev/null
records=$(wc -l <"$MANSIO_DEMO_DIR/sink.jsonl" | tr -d ' ')
echo "$records"
test "$records" -eq 2
```

`wc` prints the number of records so far, one for the publish in step 3 and one
for the first publish in step 4 (the repeats stored nothing): `2`. The point is that `jq` read every
line as a whole document. If the server is killed in the
middle of a write and the file ends without a newline, the next start refuses,
and the message names the file and the byte offset to cut it back to.

### 6. A wrong method is a 405 in the error shape (#47)

```bash
  | jq -e '.error.code == "method_not_allowed"'
```

### 7. Revoking a principal ends its leases (#19)

An agent gets a credential of its own, claims an item, and then its
credential is revoked.

```bash
agent=$(mansio principals create --kind agent --name demo-agent --tenant demo \
  --scopes '[{"topic":"work.builds","verbs":["claim"]}]' --ttl-seconds 600)
agent_id=$(jq -r .principal.id <<<"$agent")
agent_token=$(jq -r .credential <<<"$agent")
mansio work publish --tenant demo --queue builds --source ci \
  --type build.requested --data '{"sha":"abc"}'
MANSIO_TOKEN="$agent_token" mansio work pull --tenant demo --queue builds --consumer w1
mansio principals revoke --id "$agent_id"
mansio poll --tenant demo --topic facts.work | grep -F 'mansio.work.expired' | grep -F revoked
```

`work pull` prints the lease (`lease_id`, `consumer`, `expires_at`, `item`).
After the revoke, `facts.work` holds a `mansio.work.expired` fact with the
reason `revoked`, and the item is retried after its backoff, so the next
consumer is not kept waiting for the lease to run out.

Watch the lease go: the agent's credential pulls it, the admin revokes the
principal, and the engine ends the lease and writes `mansio.work.expired` with
the reason `revoked` to `facts.work`.

```services
service CLI "the agent's credential, then the admin's"
service Server "mansio-server" [[crates/mansio-server/src/credentials.rs#Credentials]]
service Engine "the work engine" [[crates/mansio-server/src/engine.rs#Engine]]
  state lease = none
service FactsWork "the facts.work topic"
  state expired = none

start "Revoking a principal ends its leases"
  > An agent pulls an item and holds a lease on it. The admin revokes the agent's principal. The engine ends the lease at once and writes an expired fact with the reason revoked, so the item is retried after its backoff and nobody waits for the lease to run out.

step "The agent pulls a lease"
  CLI -> Server: work pull, with the agent's credential [[crates/mansio-server/src/work_api.rs]]
  Server -> Engine: work_pull [[crates/mansio-server/src/engine.rs#work_pull]]
  Engine.lease = held by demo-agent
    > The lease is bound to the principal that pulled it.

step "The admin revokes the principal"
  CLI -> Server: principals revoke [[crates/mansio-server/src/principals_api.rs]]
  Server -> Engine: end_leases_of the principal [[aa21747:crates/mansio-server/src/credentials.rs#L723-L737]]

step "The engine ends the lease and writes the fact"
  Engine -> FactsWork: mansio.work.expired, reason revoked [[d1dd557:crates/mansio-server/src/engine.rs#L1393-L1429]] [[crates/mansio-core/src/work.rs#WorkFact]]
  Engine.lease = none
  FactsWork.expired = revoked
    > The item is retried after its backoff, as for any other expiry.
```

### 8. Webhooks: start at the next message, rotate, lifecycle facts (#63)

```bash
hook=$(mansio webhooks create --tenant demo --topic facts.build \
  --endpoint https://example.com/hook --start next)
hook_id=$(jq -r .webhook.id <<<"$hook")
test "$(jq -r .secret <<<"$hook" | cut -c1-6)" = whsec_
mansio webhooks rotate --id "$hook_id" | jq -e '.previous_secret_valid_until'
mansio webhooks list --tenant demo
mansio poll --tenant demo --topic facts.webhook | grep -F 'mansio.webhook.rotated'
test -z "$(mansio poll --tenant demo --topic facts.webhook | grep -F whsec_ || true)"
```

`create` prints `{"webhook":{...},"secret":"whsec_..."}` and `rotate` prints a
new secret and `previous_secret_valid_until`, each secret once. `--start next`
delivers only what is published after the webhook is made, so the two
messages already on `facts.build` are not sent. `facts.webhook` holds
`mansio.webhook.created` and `mansio.webhook.rotated`, and no secret. A
delivery to a loopback or private address is refused unless
`MANSIO_WEBHOOK_ALLOW_PRIVATE_DESTINATIONS=true`.

### 9. Metrics, the request log and the new settings (#60, #53, #57)

```bash
curl -fsS -H "Authorization: Bearer $MANSIO_TOKEN" "$MANSIO_URL/metrics" \
  | grep -Fx 'mansio_published_messages_total{tenant="demo",topic="facts.build"} 2'
curl -fsS -H "Authorization: Bearer $MANSIO_TOKEN" "$MANSIO_URL/metrics" \
  | grep -Fx 'mansio_queue_lease_expiries_total{tenant="demo",queue="builds"} 1'
curl -fsS -H "Authorization: Bearer $MANSIO_TOKEN" "$MANSIO_URL/v1/settings" \
  | jq -e '.sse_max_per_credential == 10 and .sse_max == 1000 and .snapshot_interval_seconds == 300'
```

```text
mansio_published_messages_total{tenant="demo",topic="facts.build"} 2
mansio_queue_lease_expiries_total{tenant="demo",queue="builds"} 1
true
```

The server's own terminal shows one line per request, with the method, the
route pattern, the tenant, the status, the duration and the principal, and
never a token. `MANSIO_METRICS=false` turns `/metrics` into a 404.

### 11. Fuzzing and the first release (#64, #65)

**Fuzzing** needs nightly Rust and `cargo-fuzz`, so it is shown by CI, not by a
step. The [fuzz workflow](https://github.com/ShozanHQ/mansio/actions/workflows/fuzz.yml)
runs every target for three minutes on a pull request that touches a decoder,
and weekly for longer from the
[scheduled workflow](https://github.com/ShozanHQ/mansio/actions/workflows/scheduled.yml).
It reports and never blocks: a crash is uploaded as an artifact and written to
the run's summary. To run one target yourself:

```sh
cargo install cargo-fuzz --locked
cargo +nightly fuzz run body_publish -- -max_total_time=180 -max_len=1048576
```

**The release pipeline** cannot be run on a clone: it needs the owner. Before
the first release, the owner does these once ([[README.md]], "Releases"):

1. Make an SSH signing key. Put the private key in the `release` environment as
   the secret `TAG_SIGNING_KEY`, and commit the public half as
   `.github/release-signers`.
2. Give the `release` environment required reviewers.
3. While the first release pull request (0.1.0) is open, publish 0.1.0 of each
   crate by hand, then set each crate's trusted publisher on crates.io to this
   repository, the workflow `release.yml` and the environment `release`.
4. Merge the release pull request. The owner approves the `release`
   environment's jobs three times: `publish`, `tag`, then `binaries` and
   `image`.
5. After the first image push, make the `mansio-server` package public in the
   organisation's packages settings; until then `docker pull` and the image
   checks fail for everyone but the owner.

This setup is still pending, so the demo shows the steps, not a release. After
it, "Verify a release" in the README shows how anyone checks an archive or the
image.
