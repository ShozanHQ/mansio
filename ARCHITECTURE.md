# mansio architecture

mansio is a message bus for agents, people and programs that are not connected all the time. A producer publishes facts and work to a topic; a consumer that joins later picks up what is waiting, claims a work item exactly once, or acknowledges an alert. Apache Iggy is the broker. mansio adds what Iggy does not have: per-item claim with a lease that can be extended, acknowledgement, retry with backoff, a dead topic, alert acknowledgement, and credentials the broker enforces.

## The envelope

CloudEvents 1.0 in its JSON format. Required: `specversion` (`1.0`), `id` (a lowercase hyphenated UUID, never nil; also the Iggy message id), `source`, `type`. Optional CloudEvents attributes: `subject`, `time` (RFC 3339, kept as written), `datacontenttype` (only `application/json`), `data` (JSON). `data` comes back exactly as published, so an integer wider than 64 bits, `1e2` and a long decimal are not changed. It is held as `mansio_core::Data`, which wraps serde_json's `RawValue` (the `raw_value` feature): the text of the JSON value, validated and never turned into numbers. Reading `data` removes the whitespace outside strings (`compact_json`, a small scanner) and nothing else, so a pretty-printed `data` still makes one line in the sink, the CLI and the event stream. `serde_json`'s `arbitrary_precision` was tried and not chosen: it keeps a long integer and a long decimal, but writes `1e2` back as `1e+2` (checked on `Value`). The publish route reads `data` from the request body as text (`build_envelope`), the memory and Iggy backends store the envelope's JSON, and a poll, an event stream and the sink write it back unchanged. `Data::as_str` is what was sent, and `Data::parse` reads it into a type, which has that type's limits (a `serde_json::Value` is `f64` and `u64`). The CLI and the MCP server keep it the same way: `--data` and the MCP `data` argument are checked as JSON and sent as the text given, and every answer is held as `RawValue` and printed as it came, so `mansio publish`, `poll`, `work pull` and the tools show `data` as published. Only the keys the client writes itself are reordered; the text of `data` is not. Binary `data_base64` is out of scope. On publish the server fills in `specversion`, `id` and `time` when the producer left them out. Iggy deduplicates only a client's retried requests, not message ids, so the server deduplicates on `idempotencykey` itself (see "Idempotency keys"); anything it does not deduplicate is stored again, and consumers deduplicate on `id`.

Extension attributes, all scalar as CloudEvents requires:

| Attribute | Type | Meaning |
|---|---|---|
| `tenant` | string | The tenant; the Iggy stream. Required. |
| `topic` | string | The topic it was published to. Required. |
| `principalkind`, `principalname` | string | Who published it, taken from the credential, never from the request body. Required on anything the server accepts. A kind matches `[a-z][a-z0-9_-]{0,31}`, a name `[A-Za-z0-9][A-Za-z0-9._@:+-]{0,127}`; written together as `kind:name`. |
| `correlationid`, `causationid` | string | The chain of work this belongs to and the event that caused it. Text of up to 256 bytes, no control characters. |
| `idempotencykey` | string | A producer's key. A second publish to the same tenant and topic with the same key inside `MANSIO_IDEMPOTENCY_WINDOW_SECONDS` is answered with the first and stores nothing. Carried on the envelope, so consumers can deduplicate on it too. |
| `scope` | string | The scope the action ran under, for example `work.builds:claim`. Up to 128 characters from `[a-z0-9._*:-]`. |
| `budget` | string | `<amount> <unit>`, for example `30 usd` or `200000 tokens`. The amount is a non-negative decimal of at most 24 characters, the unit a lowercase token of at most 32 characters. |
| `approvalstate` | string | `none`, `requested`, `approved` or `rejected`. |
| `recordid`, `recordprevhash`, `recordhash` | string | Set when the event came from a hash-chained log: its id there, the previous event's hash and its own (64 lowercase hex). All three or none. |
| `itemid`, `attempt` | string, integer | Work items: the stable id across retries, and the attempt number from 1. An attempt needs an item id. |

Unknown attributes are refused at the boundary. Ids, tenants, topics and principals are newtypes parsed once at the edge.

## Topics

A tenant is an Iggy stream. Its topics:

| Topic | Holds | Retention |
|---|---|---|
| `facts.<kind>` | Durable events: from a host's ledger, and every work and alert transition and every credential issued or revoked that mansio records (`facts.work`, `facts.alert`, `facts.principal`) and every delivery a webhook gives up on (`facts.webhook`). | setting |
| `work.<queue>` | Claimable items: builds, reviews, approvals, connector reads. | setting |
| `alerts` | Escalations a person acknowledges. | setting |
| `dead` | Work items past the attempt cap, and nowhere else. | setting |
| `presence` | Heartbeats and progress. Ephemeral, short expiry, never sent to the sink. | setting, short |

Segments match `[a-z0-9][a-z0-9_-]{0,62}`; so does a tenant id. Each topic has one partition, so order is publish order, and an offset counts from 0. The Iggy stream is named by the tenant id and the Iggy topic by the topic name. Topics are created on first use, by a publish, by the server's admin identity; a read never creates a stream or a topic, and a read of one that does not exist is a 404. A topic is made with a message retention set per kind of topic (`MANSIO_RETENTION_<KIND>_SECONDS`, 0 keeps forever, and a topic that keeps forever has no size cap), a segment size (`MANSIO_IGGY_SEGMENT_SIZE_BYTES`, 0 leaves it to Iggy's 1 GiB; Iggy trims a topic a whole rolled segment at a time and never the one it is writing) and a durability: `persisted` for everything that goes through the sink (`MANSIO_IGGY_DURABILITY`), `replicated` for `presence` (`MANSIO_IGGY_PRESENCE_DURABILITY`). `persisted` makes Iggy confirm a write only once it is on stable storage, so a 201 survives a crash of the host. The Iggy backend remembers the streams and topics it has found or created, and checks again for a tenant when Iggy says one is missing.

### Idempotency keys

A producer that sends again after a timeout would put the event on the bus twice, so the server remembers the keys of its publishes.

- **What is deduplicated.** A publish with an `idempotencykey` to a durable topic that a producer may publish to (`facts.<kind>` other than the ones mansio writes, and `alerts`), through the generic messages route or `alerts_publish`. If the tenant has already accepted a publish to the same topic with the same key less than `MANSIO_IDEMPOTENCY_WINDOW_SECONDS` ago, nothing is recorded in the sink or published, and the answer is 200 with the first publish's envelope and offset (a first publish is 201). The key is the tenant's, the topic's and the key's text: the same key on another topic or in another tenant is a different key, and the first envelope is read back only by the principal that published it: a repeat of the key from another principal is answered 409 with no envelope, so a credential that may only publish cannot read what others published by guessing a key. The body of the repeat is not compared with the first: the key says it is the same event. A repeat does not start a new window.
- **What is not.** A publish without a key. A key on `presence`, which is ephemeral and keeps no state. `work_publish`, which has its own rule (an item id is used once, 409). A publish whose outcome the server never learned (it answered 503 because the broker dropped the connection): the message may be stored and the key is not remembered, so a retry can store it twice, and consumers deduplicate on `id` and `idempotencykey` as before. A key whose window has ended or that was evicted by the bound, and a key whose record could not be written before a restart.
- **Memory bound.** A tenant remembers at most `MANSIO_IDEMPOTENCY_MAX_KEYS` keys, each as a pointer to the first publish (its offset, id and principal) and never its body, so the memory a tenant holds is the number of keys times a few hundred bytes, whatever was published. A repeat reads the first envelope back from the topic at that offset; if the broker never said the offset or retention has removed the message, the repeat is answered 409 naming the first id and publishes nothing. A key is dropped when its window ends (on every timer tick, and when the tenant publishes with a key) and, past the bound, the one remembered longest ago is dropped first, even inside its window. Reusing a key after its window starts a new window and moves it to the newest.
- **Across a restart.** Every remembered key is also a record in the broker's log of the server's own state (`SystemLog::Idempotency`: the `idempotency` topic of the system stream on Iggy), written after the message is stored, with the tenant, topic, key, the server's time and the pointer to the first publish. The server reads that log once when it starts (before it rebuilds the tenants, so no request waits on it), a page at a time, into the per-tenant keys, which evict by window and bound as they fill, so memory stays within the bound; records outside the window are ignored, and what is left for a tenant the broker does not list is dropped. The log is created with a message expiry equal to the window (`MANSIO_IDEMPOTENCY_WINDOW_SECONDS`, set when the log is made and set again at start-up when the setting has changed; Iggy trims whole segments, so it keeps a little more), so on disk, and in the time a start takes to read it, it is about a window's worth of keyed publishes. A broker that has no such log (`BrokerError::Unsupported`) has no keys; any other failure to read it fails keyed publishes only, remembers nothing wrong, and is tried again by the next keyed publish. A record that cannot be read is skipped with a warning. A publish whose record cannot be written is still answered and still stored, and its key is forgotten at the next restart. A crash between the message and its record has the same effect.
- **Order.** Checking the key, storing the message and remembering the key happen under the tenant's lock, so two concurrent publishes with one key store one message.

## Work items

Iggy is offset-based: it has no per-message claim, acknowledgement, redelivery or dead letters. The engine in mansio-server builds them and records every transition. An item is named by the `id` of its first message, which `work_publish` sets as `itemid` with `attempt` 1; a caller cannot set either, and the generic messages route refuses `work.<queue>` and the topics mansio writes itself: `facts.work`, `facts.alert`, `facts.principal`, `facts.webhook` and `dead`. An item id is used once: `work_publish` answers 409 for an id the queue has already had, open or done, so a resend of finished work does not run it again. The engine keeps the id of every finished item.

- **Claim** (`work_pull`) hands the oldest claimable item to the caller with a lease: a random lease id, the holder (the principal behind the credential and the consumer name from the request), the item and an expiry (now plus `MANSIO_LEASE_SECONDS`). Another caller cannot see it while the lease holds, and the claim is atomic. The lease id is the holder's proof and is never recorded: the facts carry a fingerprint of it (32 hex digits of a BLAKE3 digest), which tells which lease a fact is about and cannot be used to act under it. A consumer (the principal and the consumer name) that already holds a live lease on the queue is not given another item: it is given that lease again, with the same id and expiry, and nothing is recorded. So a client that retries a `work_pull` whose answer was lost does not leave an item leased to nobody. The server keeps the id in memory while it runs. A server that has only read the lease back from the facts cannot say the id again, so it gives the consumer a new id for the same item and expiry and records it as a second `claimed` fact of the attempt; the old id stops working. To work on several items at once, pull under several consumer names.
- **Extend** (`work_extend`) by the holder, naming the consumer and presenting the lease id, moves the end of the lease to `seconds` from now (a request's, else `MANSIO_LEASE_SECONDS`). So work that takes longer than a lease keeps its item: a consumer that extends every half lease holds it for as long as it needs, up to `MANSIO_LEASE_MAX_SECONDS` (default 86400) counted from the claim. An extension never shortens a lease, and one that asks for more than the maximum allows is capped there, not refused; the answer says where the lease ends. It is refused as an ack is: 403 for another lease id, consumer name or principal, 409 for an item with no live lease (which includes a lease that has ended before the timer has expired it), 404 for an item that is not open, and 400 for `seconds` of 0. Nothing changes then. The lease keeps its id; the `extended` fact carries its fingerprint and the new end. A request that is repeated because its answer was lost leaves the lease running to the later of the two ends, so it is safe to send again.
- **Extend and the credential.** An extension is also capped at the expiry of the holder's own credential, which the request's credential carries (`Actor::expires_at`): a credential cannot hold a lease past its own end. The admin and a credential that does not expire have no such cap.
- **Ack** (`work_ack`) by the holder, naming the consumer and presenting the lease id, completes it. Another lease id, consumer name or principal is refused with 403, an item with no live lease (never claimed, expired, waiting for its retry) with 409, an item that is not open with 404. Nothing changes then.
- **Fail** (`work_fail`) by the holder, or an expired lease, republishes the item to the same queue as a new message with the same `itemid`, `attempt` plus one and the message before as `causationid`, after a backoff of `MANSIO_BACKOFF_BASE_SECONDS * 2^(attempt-1)` capped at `MANSIO_BACKOFF_CAP_SECONDS`. When `attempt` plus one would pass `MANSIO_MAX_ATTEMPTS`, the item is published to `dead` at once instead, and nowhere else. Republished and dead messages are published by `service:mansio-engine`.
- Every transition (`claimed`, `extended`, `acked`, `failed`, `expired`, `retried`, `dead`) is an envelope on `facts.work` with the item id as `subject` and the item id and attempt as attributes; `data` names the queue, message id, attempt, and as they apply the lease (its fingerprint), holder, consumer, expiry, reason and what happens next (`next`, `retry_at`). It is recorded in the sink first and then published.

A timer (`MANSIO_TICK_MILLIS`) drives expiries, republishes and the surfacing of alerts. It reads the clock through a trait, so tests move time by hand.

### State

The engine keeps, per tenant, the open items of each queue, the ids of finished ones (16 bytes each), their leases and the alerts, and the ids of acknowledged alerts. None of it is authoritative: it is a projection of `work.<queue>`, `facts.work`, `dead`, `alerts` and `facts.alert`. On start the server lists the tenants and topics the broker holds (`Broker::tenants`, `Broker::topics`), reads those topics from offset 0, or from the offsets of the tenant's snapshot if it has a usable one, and rebuilds the state (Iggy 0.9 answers an offset below the first message that retention has left with that message, so a topic whose head was trimmed is read in full from what remains; the `Broker::poll` contract says so and a CI test against Iggy pins it); a tenant it first meets later is rebuilt on its first request. An item's newest message says what it is, and the transitions recorded for that attempt say where it stands: a lease still holds until the latest expiry recorded for it by its `claimed` and `extended` facts, and the longest it may run is counted from the first `claimed`; a failure waits until its recorded `retry_at`. So a restart neither drops nor duplicates an item, and a lease that ended while the server was down is expired on start. Order is by position in the queue, not by offset, because Iggy does not always report one. A message that cannot be read is skipped with a warning naming tenant, topic and offset, and does not stop the tenant: the page it is in is read again one message at a time, and the next page whole. The server answers nothing, `/healthz` included, until it has tried to rebuild every tenant it found, so a long replay keeps `/healthz` dark; the compose health check has a start period for that (`MANSIO_HEALTH_START_PERIOD`). Snapshots (below) keep that replay short.

### Snapshots

A start that reads every topic from offset 0 takes as long, and as much memory, as the tenant has history. So the engine writes a snapshot of each tenant's state, and a start reads the snapshot and then only the messages after it.

- **What a snapshot covers.** The tenant's state as `state.rs` holds it: for each queue the open items (each item's newest message, its position in the queue, and its phase: claimable, leased with holder, consumer, expiry and the time the lease began, waiting out a backoff, or owed a fact with the fact itself), the ids of finished items, the alerts nobody acknowledged with when each was accepted or last surfaced, and the ids of acknowledged alerts. With it, for each replayed topic (`work.<queue>`, `facts.work`, `dead`, `alerts`, `facts.alert`), the offset of the first message it does not cover.
- **What it does not.** A lease id, which only its holder has (a lease read from a snapshot, like one read from the facts, is given a new id when its holder asks again); the idempotency keys, which have their own log; and anything on `presence` or another `facts.<kind>`, which the engine does not replay.
- **When one is written.** `MANSIO_SNAPSHOT_INTERVAL_SECONDS` (default 300; 0 writes none) after the last one, or after the state was rebuilt, and only if the tenant's state changed since. The server notes where each of its own publishes landed; a publish the broker did not say the offset of, or that landed away from where the state expected it, leaves the state not knowing what it covers, and no snapshot is taken of it until it is rebuilt. The state is copied under the tenant's lock, as one moment, and written without it.
- **Where.** One file per tenant, `<tenant>.json`, in `MANSIO_SNAPSHOT_DIR` (default `mansio-snapshots`, `/data/snapshots` in the image; empty keeps none), written to a temporary file, synced and renamed over the last, so a reader sees a whole one. Only the newest is kept.
- **Start.** The server reads the snapshot, reads each topic from its offset, and brings the state up to date: a new message is a new item or a newer version of one the snapshot holds, and a fact moves the item it is about from where the snapshot left it (a lease's start is kept from the snapshot). The result is the state a read from offset 0 gives; the tests compare the two.
- **A snapshot is a cache.** One that cannot be read, is of another format or tenant, names a topic that is not one, or covers offsets a topic no longer reaches (checked with one read at the last offset it covers) is dropped with a warning and the state is rebuilt from offset 0. A write that fails is logged and tried again after the next interval.
- **Retention.** A snapshot reads `facts.work` only after its offsets, so it cannot make up for facts that retention deleted before them; a `facts` retention shorter than that of `work` leaves items whose message is kept and whose facts are gone, and a start offers them again. The server checks `MANSIO_RETENTION_FACTS_SECONDS` against `MANSIO_RETENTION_WORK_SECONDS` when it starts and logs a warning if the first is the shorter (forever counts as the longest). It checks the settings it creates the topics with, not the retention an operator later set on a topic in Iggy.

A transition is written before the state changes, so a write that fails changes nothing. But a publish that fails without a refusal, because the broker could not be reached or its answer does not say whether it applied the write, does not say the message was not stored (the connection may drop after the write), so after one the tenant's state is thrown away and rebuilt from the logs on its next use. A refusal is a definite answer and does not rebuild anything. The timer ends its pass for a tenant after the first such failure, so a broker that cannot be reached costs one rebuild per tick, however much is due. An alert keeps the time it was accepted or last surfaced through a rebuild. That finds a stored item, acknowledgement or claim whatever the caller was told.

Republishing an item and sending it to `dead` each publish a message and then record a fact, which cannot be one write. Between the two the item is not claimable and owes its fact; the timer finishes it, and so does a restart, which finds the message published and the fact missing and records the fact once. A message that was never published is published once. The fact that is owed is made from its message alone: its id is the message's id with a fixed pattern mixed in, and its time is the message's time. A restarted server makes the very fact the stopped one would have, so if the sink had already recorded it, the second record has the same `id` and a consumer that deduplicates on `id` sees one.

The timer works through what is due in a tenant one task at a time. A task that fails is logged and left for the next tick, and the others go on, so one item the broker keeps refusing does not hold up the rest.

The ids of finished items and acknowledged alerts are all that is kept of them, and they only grow while the server runs. A restart rebuilds them from the topics, so what bounds them is `MANSIO_RETENTION_WORK_SECONDS` and `MANSIO_RETENTION_ALERTS_SECONDS`; with the default of keeping forever they are unbounded, and an id older than the retention can be used again.

A publish that fails with a 503 may have been stored: the broker could not be reached, or it answered in a way that does not say whether it applied the write (the Iggy client writes a request before it reads the reply, so a reply it cannot decode follows the write). So a client of `work_publish` or `alerts_publish` that gets a 503 resends with the same `id`; a 409 then means the first attempt was stored. A refusal the broker named before it stores anything (a 502) is definite: nothing was stored and the state is left as it is. Only the statuses the Iggy backend knows to precede the write are a refusal (an unauthorized request, an invalid identifier, a message count or payload size it refuses); every other Iggy error is a 503.

The engine is one process's view of a tenant: its lock and its state are in memory, so claims are atomic within one mansio-server. More than one mansio-server on a broker is safe only with tenant ownership, below; without `MANSIO_OWNER_TTL_SECONDS` two servers on the same broker could give the same item to two consumers.

Retention must keep `facts.work` at least as long as `work.<queue>`: an item whose facts expired while its message did not is claimable again.

### Servers that share a broker

**Decision.** Several mansio-servers can share one Iggy by partition ownership per tenant, fenced through the broker: a tenant has one owner at a time, only its owner serves it, and a server that stops hands its tenants to another within `MANSIO_OWNER_TTL_SECONDS`. Rejected: a lease per item through the broker (Iggy has no conditional append, so every claim would need a round trip and a read to learn whether it won, and the state would still be in every server's memory); and one Iggy partition per tenant read by a consumer group, which would tie the tenant's share of work to Iggy's rebalancing and give the engine no place to keep leases. Iggy's own clustering is out of scope, and so is balancing: a tenant goes to whichever server asks first, and the others stand by.

- **The log.** The owners log is a system log (`SystemLog::Owners`, the Iggy topic `owners` of `mansio.system`, kept forever like the other system logs, because a view is a fold from a tenant's first claim), which has one partition and so one order that every server reads the same. Every server reads all of it and folds it into a view per tenant (`ownership.rs`): the owner, an `epoch` that goes up by one with each change of owner, a `beat` that goes up with each renewal, and when this server last saw the view change, by its own clock.
- **Compare-and-set from an append and a read.** `claim` takes a tenant at `epoch + 1` and names the `beat` it was made against. It counts only if the view's beat is still that when the claim is reached in the log: of two claims against one beat the first in the log wins, and a claim made against a beat the owner has renewed since is refused. `renew` moves the beat of every tenant its server owns, in one record; it counts only for the owner at its epoch, so a renewal that comes after another server's claim counts for nothing. `release` gives tenants up. A server serves a tenant only after it has appended its claim or renewal and read it back as accepted.
- **When a tenant is taken.** A server takes a tenant nobody owns, or whose view has not changed for `MANSIO_OWNER_TTL_SECONDS` by the taker's own clock. It times how long it has watched and not what a record says, so the servers' clocks need not agree. A server that starts has watched for nothing and so waits out the ttl for a tenant a crashed server held. Owners renew every quarter of the ttl, so a server that stops hands its tenants over within the ttl plus a quarter, and at once if it stops in order, because it appends a `release` after it has stopped serving.
- **Fencing.** A server serves a tenant until half the ttl after the start of the round that last proved it the owner. The taker cannot act before the whole ttl has passed since it saw the owner's view last change, which is after that round began, so the old owner has stopped by then even if it is slow, and the margin is half a ttl for clocks that run at different speeds and for the time a request takes. Every durable write checks this again just before it goes to the broker, and a request for a tenant served elsewhere answers 503 `unavailable`, which a client sends again as it does for any 503; a load balancer in front sends it to the other server. The one thing not fenced is a request that stalls for more than half a ttl between that check and the broker's answer, because the broker has no conditional append.
- **Handover loses nothing.** The taker rebuilds the tenant's state from its topics, as a restart does, so a lease the old owner gave is still held until it ends, then expires and is retried, and an item that was waiting is claimable. A state is rebuilt whenever the epoch it was built at is not the epoch it is served at, and a tenant's idempotency keys are read again from the log, because the other server may have published with keys. Snapshots are a cache and are per server, so the taker uses its own and replays from its offsets.
- **Clocks.** Every duration the ownership code measures (the time to serve, the taker's wait, the interval between rounds) is read from a monotonic clock, so a step of the system clock, from NTP or by hand, moves no fence. Leases and backoffs stay on the wall clock, because they are written to the log as absolute times.
- **Credentials follow the log.** The registry of principals is read from its log on first use and then tailed: at every credential sweep (`MANSIO_CREDENTIAL_SWEEP_SECONDS`), and at once, at most once a second, when a token is presented that the registry does not know. So an agent credential issued through the owner works on the server that takes over, and a revocation made on one server reaches the other.
- **What is not shared yet.** The webhooks and the consumer positions are read when a server starts, so a webhook or a named consumer made through one server is known to another only after that restarts, a consumer position committed on one is not seen by the other (it re-reads from the position it last loaded), and a webhook is delivered by every server that holds it. Making these follow the owner is for later work. A request still running when a server's shutdown grace ran out is fenced only by the check before its write, like a request that stalls.
- **Off by default.** `MANSIO_OWNER_TTL_SECONDS` is 0, which keeps today's behaviour: the server serves every tenant and must be the only one on its broker. Set it, to the same value, on every server that shares a broker.
- **Tests.** `ownership.rs` tests the log's rules with a clock moved by hand. The engine tests run two engines on one broker: pulls over both never claim an item twice, and a stopped engine's tenant, with an item leased and others waiting, is taken by the other with every item done once. The end-to-end suite runs two servers (in process, and in CI two containers on one Iggy, `docker compose --profile ha`): a race for a fresh tenant, pulls spread over both, then the owner killed without warning, the other serving within the ttl and every item done once (`mansio-e2e/tests/e2e/ha.rs`).

## Alerts

Published to `alerts` (`alerts_publish`, or the generic route to `alerts`). The alert is the message and its id is the message's `id`; an id is used once, and a resend of one the tenant has is refused with 409, so a resend cannot reopen an acknowledged alert. `alerts_ack` by a principal records who and when as `facts.alert` `acknowledged`; a second ack is refused with 409, and the first in the log is the one that counts. An alert unacknowledged `MANSIO_ALERT_RESURFACE_SECONDS` after it was published is surfaced again as `facts.alert` `resurfaced`, once per interval until it is acknowledged. The interval runs from the server's clock when it accepts the alert, not from the `time` the producer wrote; after a restart it runs from the last `resurfaced` fact, or else from the alert's own `time`, or from the restart if that is in the future. Once acknowledged, an alert is kept in memory as its id only.

## Sink

`Sink::record(&Envelope) -> Result<Option<Record>>` is called before every durable publish mansio makes, in order. A host returns the record it appended (id and hashes), which is set on the envelope before it is published, so subscribers can verify it against the host's log. The standalone binary uses a JSON Lines file sink (`MANSIO_SINK_PATH`) and returns no record. A record a producer put on the envelope is kept when the sink returns none and replaced when it returns one.

Record and publish happen under one async lock per tenant, so the sink sees a tenant's messages in the order its topics hold them, whichever route they took. A failed publish after a record leaves the record in the sink with nothing on the topic.

## Credentials

A principal is a kind (`person`, `agent`, `connector`, `service`, or another lowercase token), a name and a tenant, with scopes: a topic pattern (a topic, `facts.*` or `work.*`) and verbs (`publish`, `subscribe`, `claim`, `ack`, `approve`). A kind and a name name one principal in a tenant. The admin API (`principals_create`, `principals_list`, `principals_revoke`) issues the credential: a user of the broker that may read the topics of its tenant's stream that its scopes cover, and a personal access token of that user, which is the credential. Only the bootstrap token, now the admin principal's credential (`MANSIO_TOKEN`), compared in constant time and standing for `MANSIO_TOKEN_PRINCIPAL`, may call it.

**A credential reads; the server writes.** The principal on an envelope comes from the credential and never from what the caller writes, and neither do `itemid` and `attempt`. A user of the broker that could send could write any of them, and any fact on a topic it may send to, so a credential's user is given poll permission and never send. Every write goes to the server, which checks the `publish` scope, sets the principal from the credential and publishes as its own admin identity. A credential that talks to the broker directly can read what it may and write nothing.

**Verbs.** `publish` lets the holder write through the server (`messages`, `work_publish`, `alerts_publish`), on any topic except the ones only mansio writes: `facts.work`, `facts.alert`, `facts.principal`, `facts.webhook` and `dead` (`Topic::is_written_by_mansio`). A scope naming one of those with `publish` is refused when it is made, and `facts.*` with `publish` skips them. `subscribe` and `claim` are the broker's poll permission; `claim` and `approve` (on `work.approvals` only) also let the holder `work_pull` from the queue and `work_extend`, `work_ack` or `work_fail` its own leases; `ack` (on `alerts` only) lets it `alerts_ack`. The broker has no word for publish, claim, approve or ack, so mansio enforces them. A verb on a pattern it cannot apply to is refused when the scope is made.

**In the broker.** An Iggy permission names a topic by number. `IggyBroker` expands a pattern to the topics the tenant has, remembers each user's scopes, and works out again what every user of the tenant may read when a topic is made, and of every tenant when a stream is made, because Iggy may give a new stream or topic the number of a deleted one; a user whose stream is gone has no permissions. `MemoryBroker` evaluates the same scopes. A permission is never given on a stream as a whole, or globally. The server's own Iggy user, made by `provision-admin` with root credentials that the server is never given, manages users and streams and reads and writes every topic. It creates streams and topics, on a publish; a read creates nothing.

**Who is asking.** A bearer is the admin token, or a credential: a digest of every credential issued is in the registry, so a token that was never issued, or was revoked, is refused without any traffic to the broker. For one that is known, the expiry is checked against the server's clock, and the broker is asked whether it still accepts the token and whose it is, at most every `MANSIO_CREDENTIAL_RECHECK_SECONDS`, so a revocation or an expiry the server did not itself see applies within that time. Only an answer from Iggy that says the token is bad (invalid or expired token, invalid credentials, not authenticated, user inactive or not found, invalid format) is a 401 and ends a kept session; any other failure to sign in is a 503, so a valid credential is never refused for good by a fault that is not its own. Identity is the credential's and nothing in a request. The server reads for a credential through a client signed in with it (`Caller::Credential`, one client per credential in use), so the broker refuses what the scopes do not allow, and a refusal is a 403. A request is also checked against the scopes before anything is recorded or created, and before the engine holds state for the tenant it names, so a refusal leaves nothing behind; `work_pull` additionally reads the queue as the caller before a lease is handed out.

**Sessions.** Iggy checks a token when it signs in and not afterwards, so a session a holder opened before a revocation or an expiry is not ended by Iggy. A revocation deletes the user, which takes away what it may read at once. An expiry is enforced by the server at once and by the broker when the sweep deletes the user: the bound is `MANSIO_CREDENTIAL_SWEEP_SECONDS`, and only while the server runs. A user that is signed in can make tokens for itself, with any expiry; they end with the user.

**Issue.** Recorded first: the `created` fact goes to the sink and `facts.principal`. Then the broker makes the user, with a random password nobody is told and that is dropped once the token is made, and the token with the expiry (an `agent` always has one: `MANSIO_AGENT_CREDENTIAL_TTL_SECONDS`, or the request's). Then the registry log is written. If a step after the fact fails, the user is deleted, a `revoked` fact with the reason `failed` closes it, and no credential is returned. The credential is returned once; no log, fact or record holds it.

**Registry.** The principals are a projection of a log in the broker that no credential can reach (the Iggy stream `mansio.system`, topic `principals`, whose name is not a valid tenant): `created` with the principal, its broker user and the digest of its credential, and `revoked`. It is read when first needed. Every principal in it is told to the broker again, because the broker keeps scopes in memory. One the broker cannot find the user or tenant of has its user deleted, and then is withdrawn; if the delete fails it is kept and tried again at the next start. Every broker user named like one made for a principal (`mansio-` and 32 hex digits) that no record owns is deleted: one that was made just before the server stopped. That is only done once the whole log has been read. A record that cannot be read (damaged, or written by a newer version of the format) fails the load instead: it logs the offset and the reason at `error`, every credential gets 503 (not 401), `/healthz` says `degraded`, and nothing is deleted or revoked for it, because a principal whose record is unreadable must not look like an orphan. The load is tried again after `MANSIO_CREDENTIAL_RECHECK_SECONDS`, by whichever request, health check or sweep comes first, so the log is read and the failure logged once an interval and not once a request. Each record carries its format version in `v` (1 when absent), and an earlier version is read as it was written: fields it does not know are ignored, and a scope is taken as stored and not checked against the rules for a new one, so tightening those rules never turns a principal into an orphan.

The server keeps two more logs there, in the same stream: `webhooks`, the registry of webhooks, which holds each webhook's signing secret (kept nowhere else and returned once), and `cursors`, the position of every named consumer and webhook.

**Revoke and sweep.** The broker's user is deleted first, which ends its token and takes away what it may read, and the revocation holds from then on whatever else fails. Then the principal leaves the registry and its log, and `revoked` is recorded (reasons `requested`, `expired`, `failed`). A sweep every `MANSIO_CREDENTIAL_SWEEP_SECONDS` revokes the expired, as `service:mansio-engine`.

**Leases of a revoked principal.** Once a principal has been revoked, and recorded, the engine ends every live lease its `kind:name` holds in the principal's tenant (`Engine::end_leases_of`), under the tenant's lock: each is an `expired` fact with `reason` `revoked`, and the item goes through the backoff as for any expiry, to a retry or to `dead` at the attempt cap. The sweep revokes through the same path, so an expired agent credential's leases end when the sweep removes it, and not when the longest lease runs out. A lease that had already run out is left to the timer, and an item whose lease cannot be ended (the broker cannot be reached) is logged and left to it too: the revocation stands either way. The `expired` fact says `revoked` and not whether it was asked for or the credential's expiry passed: `facts.principal` says which.

The bootstrap token's principal (`service:mansio` by default) and `service:mansio-engine` cannot be issued. The server sets `tenant`, `topic`, `principalkind` and `principalname` from the path and the credential's principal, and refuses a body that carries any of them.

## Surfaces

One HTTP API under `/v1`:

- `GET /healthz`, open: `{"status":"ok"}`. While the registry of principals is not loaded it answers 503 `{"status":"degraded","credentials":"unavailable","message"}`: the server is up and no credential is accepted (the admin token still is). While the registry of webhooks is not loaded it adds `"webhooks":"unavailable"`: no webhook is delivered and the webhooks admin API answers 503. The cause is in the log, at `error`; a health check that keeps asking drives the retry (see Registry and Webhooks).
- `POST /v1/tenants/{tenant}/topics/{topic}/messages`: the body is an envelope without the four attributes above; the answer is 201 with `{"offset", "envelope"}`, the envelope as stored. `offset` is absent when Iggy stored the message without saying where and it is not among the last `MANSIO_IGGY_LOCATE_WINDOW` messages: the message is stored, so the client must not send it again.
- `GET /v1/tenants/{tenant}/topics/{topic}/messages?offset=N&count=M`: 200 with `{"messages": [{"offset", "envelope"}]}` from that offset, in publish order.
- `GET /v1/settings`: the effective non-secret settings (the work, credential, stream and webhook settings and the API limits).
- `work_publish`: `POST /v1/tenants/{tenant}/work/{queue}/items`, an envelope without the server-set attributes and without `itemid` and `attempt`; 201 as for a publish.
- `work_pull`: `POST /v1/tenants/{tenant}/work/{queue}/pull` with `{"consumer"}`; 200 with `{"lease_id", "consumer", "expires_at", "item"}`, or 204 when nothing is claimable. A consumer that holds a live lease is answered with it again.
- `work_extend`: `POST /v1/tenants/{tenant}/work/{queue}/items/{itemid}/extend` with `{"lease_id", "consumer", "seconds"?}`; 200 with the `extended` fact's envelope, whose `data.expires_at` is where the lease now ends.
- `work_ack`: `POST /v1/tenants/{tenant}/work/{queue}/items/{itemid}/ack` with `{"lease_id", "consumer"}`, and `work_fail`: `.../fail` with `{"lease_id", "consumer", "reason"}`; 200 with the transition's envelope.
- `alerts_publish`: `POST /v1/tenants/{tenant}/alerts`, as a publish to `alerts`. `alerts_ack`: `POST /v1/tenants/{tenant}/alerts/{id}/ack`; 200 with the `acknowledged` envelope.
- `consumers_get`: `GET /v1/tenants/{tenant}/topics/{topic}/consumers/{consumer}`; 200 with `{"consumer", "offset"?, "next"}`. `consumers_commit`: `POST .../consumers/{consumer}/commit` with `{"offset"}`; 200 with the same, or 409 if no message exists at or after the offset. Needs the right to read the topic; the consumer is the caller's own.
- `GET /v1/events?tenant=&topic=[&from=]`: server-sent events, see below.
- `principals_create`: `POST /v1/principals` with `{"kind", "name", "tenant", "scopes", "ttl_seconds"?}`; 201 with `{"principal", "credential"}`. `principals_list`: `GET /v1/principals?tenant=`; 200 with `{"principals"}`. `principals_revoke`: `DELETE /v1/principals/{id}`; 200 with the principal. The admin credential only.
- `webhooks_create`: `POST /v1/webhooks` with `{"tenant", "topic", "url"}`; 201 with `{"webhook", "secret"}`. `webhooks_list`: `GET /v1/webhooks?tenant=`; 200 with `{"webhooks"}`, each with `last_delivered_offset` and `last_error`, and no secret. `webhooks_delete`: `DELETE /v1/webhooks/{id}`; 200 with the webhook. The admin credential only.

Every refusal is `{"error": {"code", "message"}}` with 400 (malformed), 401 (no valid token), 403 (a valid credential that may not do this, or a lease that is not the caller's), 404 (including a read of a topic nobody has published to), 405 (the route does not take that method), 409 (the state does not allow it: no live lease, an alert already acknowledged, an item or alert id already used, a principal that already has a credential), 413 (body too large), 500 (a fault in the server: the message is generic and the cause is logged), 502 (the broker named a refusal that comes before it stores anything: nothing was stored) or 503 (the broker or the sink is unavailable, or the broker's answer does not say whether it applied the request: send it again with the same id). A 502 or 503 is logged at `warn` with the tenant, topic and cause. Everything but `/healthz` needs `Authorization: Bearer <token>`.

Length limits are in bytes; a value over its limit is a 400. Free text is not empty and has no control characters: `source` and `subject` 1024; `type`, `correlationid`, `causationid`, `idempotencykey`, `itemid` and `recordid` 256. A tenant id and each topic segment 63, a principal kind 32, a principal or consumer name 128 (`crates/mansio-core/src/id.rs`); `scope` 128 characters from `[a-z0-9._*:-]`; in `budget` the amount 24 characters and the unit 32.

### Consumers

A named durable consumer is a position: the offset of the last message the consumer handled, so it reads next from one after it, or from 0 if it has committed none. mansio keeps every position itself, in the `cursors` log of the system stream (a `named` record: tenant, topic, principal, consumer name and offset; and a `webhook` record: webhook id and offset), read when first needed and replayed on start, a record written before the position changes. No position is given out before the whole log has been read: a caller that asks while it is being read waits for it, so that a server that starts several webhooks at once does not send any of them its topic again from the first message. It does not use the broker's own consumer offsets: Iggy lets any user that may read a topic store an offset for any consumer of it, so a credential that reads a topic could move another consumer, or a webhook, on. A named consumer belongs to the principal behind the credential, so its key is tenant, topic, principal and name, and two principals that use one name have two positions that neither can read or move. A webhook's position is its own record and is not reachable through the consumers API. The log is not trimmed: it grows by a record for each commit that changes a position.

`consumers_get` and `consumers_commit` need the right to read the topic: the server reads it as the caller first, so the broker holds a credential to its scopes, and a topic that does not exist is a 404. A commit is refused with 409 if no message exists at or after the offset (an offset past the last message, or any offset of an empty topic): the server reads the topic from that offset as its admin identity, and so this is the same on every broker. An earlier offset sets the consumer back, and one that retention has deleted is accepted.

### Server-sent events

`GET /v1/events?tenant=T&topic=X` serves the topic as `text/event-stream`: each event's `id` is the offset, `event` the envelope's `type` and `data` the envelope JSON. It starts at `?from=` (default 0) or, if the client sends `Last-Event-ID`, which wins, one after that offset, so a reconnecting client misses nothing and sees nothing twice. It is authorised as `poll` is, before the first byte, with the caller's credential, which the broker holds to its scopes on every read after: a credential that is revoked while the stream is open ends it. The server looks for new messages every `MANSIO_STREAM_POLL_MILLIS`, and sends a comment every `MANSIO_SSE_KEEPALIVE_SECONDS` when there is nothing else. Open streams are counted (`stream_limits.rs`) after authorisation and before the first read: a credential at `MANSIO_SSE_MAX_PER_CREDENTIAL` gets 429, and the server at `MANSIO_SSE_MAX` answers 503; the stream holds its place until it is dropped. A message that cannot be read is skipped with a warning: the stream, the webhooks and the rebuild of the engine's state read a topic with the same reader (`tail.rs`), which reads a page and, if it fails, the page again one message at a time. On shutdown the signal that stops the listener also ends every stream, because a stream never ends by itself and the graceful shutdown waits for every connection; it then waits at most `MANSIO_SHUTDOWN_GRACE_SECONDS` for the requests still being served and stops anyway. A host that mounts the routes itself gets an `Ender` from `Server::build` and calls it when it begins to stop. A credential that is revoked ends its stream at the next read; one that expires does when the sweep deletes its user.

### Webhooks

The admin API registers a webhook (`webhooks_create`: tenant, topic, URL) and returns its signing secret once; `webhooks_list` shows each with its last delivered offset and last error and no secret; `webhooks_delete` removes it. The registry is a projection of the `webhooks` log of the system stream (`created` with the webhook and its secret, `deleted`), loaded when first needed and on start, which is the only place a secret is kept.

Each webhook has a task that follows its topic from its position in the `cursors` log, from the first message the topic holds on its first run and from one after the position after, and POSTs each envelope in offset order, one at a time, as `application/cloudevents+json` (structured mode) with `mansio-signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<body>">`, the key being the secret's text and `t` the moment of that attempt. A 2xx, then the commit of the offset. Any other answer, a timeout (`MANSIO_WEBHOOK_TIMEOUT_SECONDS`) and a connection that fails retry after `MANSIO_WEBHOOK_BACKOFF_BASE_SECONDS * 2^(attempt-1)` capped at `MANSIO_WEBHOOK_BACKOFF_CAP_SECONDS`; a redirect is not followed. After `MANSIO_WEBHOOK_MAX_ATTEMPTS` the delivery is recorded as `mansio.webhook.failed` on `facts.webhook` (recorded in the sink first, by `service:mansio-engine`: the webhook, topic, offset, message id, attempts and error, never the address) and the webhook commits the offset and moves on; if the fact cannot be recorded it tries again until it can. Delivery is at least once: a stop between the answer and the commit sends that envelope again, and the envelope's `id` is how a receiver deduplicates. `last_error` is kept in memory and stays until another attempt fails; `last_delivered_offset` is the last offset the receiver accepted, or after a restart the committed offset until the next delivery. `facts.webhook` cannot be delivered, as a failure would be delivered to itself. The id of that fact is made from the webhook's id and the message's, as an owed fact's is from its message's, so a give-up recorded again after a restart is the same fact. The address is at most `MANSIO_WEBHOOK_URL_MAX_BYTES`.

The registry of webhooks fails loud, as the principals' does, because it is the only copy of the secrets and of what was deleted: each record carries its format version in `v` (1 when absent, `records.rs`), and one that cannot be read (damaged, or of a newer version) keeps the registry unloaded. Skipping a `deleted` record would revive a webhook that delivers to an address the admin removed; skipping a `created` one would lose its secret. While it is unloaded the admin API answers 503, `/healthz` is `degraded`, and no delivery task starts; the load is tried again after a wait that grows from `MANSIO_WEBHOOK_BACKOFF_BASE_SECONDS` to its cap and is logged at `error` when a run of failures starts and again when its cause changes. The `cursors` log is versioned the same way but skips a record it cannot read, with a warning, because the cost is a position that is older and a message seen again, which delivery already allows. A task that cannot read its position or its topic, or record a delivery it gave up on, waits with the same growing wait and logs once when the run of failures starts and once when it ends.

### The CLI and the MCP server

`mansio` has one command for each operation above, named as the operation with `_` as a space (`mansio work pull`), and `mansio mcp` serves every one but `watch` as an MCP tool on stdio with the operation's name (`work_pull`) and the command's flags, `_` for `-`, as its input. Both are generated from one description of the operations and run one implementation of each, in the `mansio` crate (`ops.rs`); a test reads back the commands and the tools and fails on any difference beyond `watch`, which streams, and `mcp`. The MCP server accepts a batch of JSON-RPC messages (the 2025-03-26 revision requires it) and answers a line that is not UTF-8 or not JSON with a parse error. They need a token (`MANSIO_TOKEN` or `--token`) before they send anything. They retry a request that failed on the network, always if the connection was not made and otherwise only if the request is safe to repeat: a read, `work_pull`, `work_extend` and `consumers_commit`.

`mansio watch` polls the topic over the HTTP API every `MANSIO_POLL_INTERVAL_MILLIS`. With `--consumer` it takes where to start from `consumers_get` and commits each offset (`consumers_commit`) after the line has been written and flushed; on SIGINT or SIGTERM it finishes the line it is on, commits it and exits 0; a second signal while it does ends it at once, without the commit.

## Settings

Every limit, interval and switch is a named setting read from the environment with a default, listed in the README. No constant stands in for a setting.
